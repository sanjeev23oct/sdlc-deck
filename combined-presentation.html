AI IN THE SDLC05 / 24
HOW / AVOIDING VIBE CODING

An unstructured prompt
leaves decisions implicit.

Example request: “Let an RM download a pre-meeting report.”

Prompt straight to code

The agent may guess who has access, what data to include and how missing sources should behave.

Specification before code

The team decides access, report content, missing-data behavior and acceptance checks before implementation.

Exploration can start in chat. Delivery needs an agreed specification and reviewed changes.

HOW / SKILLS IN PRACTICE / 1 OF 2

Without a shared skill:
the prompt leaves the rules open.

Illustrative output from a short prompt. The agent may choose a different implementation.

SAME TASK“Create a .NET API to add a client.”
EXAMPLE 01

Controller structure

Possible implementation sketch
db.Clients.Add(request);
await db.SaveChangesAsync();
return Ok(request);
The review discovers: database access in the controller, no explicit DTO boundary and a response that may differ from the team’s creation contract.
EXAMPLE 02

Validation and errors

Possible failure handling
catch (Exception ex) {
  return BadRequest(ex.Message);
}
The review discovers: mixed business and system failures. Access rules, field validation and the approved error format still need decisions.
EXAMPLE 03

Tests and evidence

Possible generated test
CreateClient_ValidInput_ReturnsOk();
The review discovers: one happy-path check. Invalid input, denied access and failure cases lack evidence. The test may repeat the implementation’s assumption.
The developer repeats team rules in chat, requests fixes and reviews the revised behavior again.

Controller structure

Skill: DTO + service boundary + creation contract
CreateClientRequest → clientService.CreateAsync()
return CreatedAtAction(..., responseDto);
Expected output: a thin controller and the agreed response shape.
Evidence: review of boundaries and a check for 201 plus the agreed Location behavior.
EXAMPLE 02

Validation and errors

Skill: apply approved access and error rules
Apply agreed authorization policy
Validate request fields
Use the team’s ProblemDetails mapping
Expected output: explicit validation and consistent errors.
Evidence: invalid input, unauthenticated and forbidden-access checks, as applicable.
EXAMPLE 03

Tests and evidence

Skill: verify acceptance and report results
201: valid create · 400: invalid fields
401 / 403: access cases
Record executed checks and results
Expected output: tests tied to requirements and a change summary.
Evidence: actual results linked to the change. Report failed or unexecuted checks openly.
Expected impact: less repeated prompting, more consistent changes and clearer review evidence. Skills still need tests and human review.
